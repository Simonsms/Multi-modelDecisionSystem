# 后端接口清单与数据表草案

**文档日期**：2026-04-08  
**文档目标**：基于当前已确认的 GUI 工作台、多模型阶段式架构和 MVP 页面结构，收敛第一版后端接口契约、核心数据表与页面映射关系  
**适用范围**：后端选型评估、前后端对接、数据库初版建模、埋点预留

---

## 1. 核心判断

第一版后端不应该先追求“大而全平台”，而应该先服务已经确认的这条主链路：

```text
需求梳理 -> 调研分析 -> 方案比较 -> 决策建议
```

所以这版后端设计的重点只有四个：

1. 支撑 GUI 工作台按阶段稳定推进
2. 支撑多模型按角色参与，并保留运行记录
3. 支撑候选方案、证据、建议的结构化沉淀
4. 为后续埋点和分析后台预留稳定口子

---

## 2. 后端契约设计原则

## 2.1 先用 REST 固化主契约

当前阶段建议先把浏览器到后端的主契约定义为 **REST API**。

原因很直接：

- 前后端边界清楚
- 便于先把页面数据喂起来
- 不被具体技术栈绑死
- 更适合先做“工作台可用”而不是“实时系统炫技”

## 2.2 运行态更新预留实时通道，但不强绑实现

工作台页后续一定会需要运行态更新，例如：

- 阶段执行中
- 模型调用中
- 阶段完成
- 重跑失败
- 推荐生成完成

因此建议的通信形态是：

- 主数据读写：`REST`
- 运行态更新：`WebSocket` 或 `SSE`
- 第一版兜底：`短轮询`

当前文档只先固化资源接口，不强行锁死实时协议。

## 2.3 全链路必须能追踪

为了后续审计、问题复盘、成本分析和埋点，第一版所有关键动作都建议带上以下链路标识：

- `sessionId`
- `stage`
- `stageRunId`
- `runId`
- `recommendationId`
- `candidateId`

其中建议：

- `sessionId` 表示一次决策会话
- `stageRunId` 表示某个阶段的一次执行
- `runId` 表示某次具体模型或子任务运行

## 2.4 先采结构化行为，不先采全文

你已经明确：用户采集方案后置，但不能忘。

因此第一版接口和数据表只预留这些最小采集能力：

- 谁在什么阶段做了什么动作
- 哪个模型在什么角色下被调用
- 某次阶段执行的状态、耗时、成本
- 推荐是否被采纳、退回或重评估

默认不采：

- 用户原文全文
- 模型输出全文
- 推理链全文
- 高敏感原始 trace

## 3. 资源模型总览

第一版后端建议围绕以下资源组织：

- `Session`
- `StageRun`
- `ResearchItem`
- `Evidence`
- `CandidateOption`
- `DecisionRecommendation`
- `ModelInvocation`
- `UserAction`
- `UsageMetric`

补充说明：

- 阶段产物快照先挂在 `StageRun.resultSnapshot`
- 页面需要的聚合视图由聚合接口返回，不要求前端自行拼装所有明细
- 对比矩阵第一版可以先作为聚合结果，不急着独立成复杂表

## 4. 接口设计约定

## 4.1 基础约定

- Base Path：`/api/v1`
- 返回格式：建议统一返回 `data`、`meta`、`error`
- 时间字段：统一 ISO 8601
- 列表接口：统一支持 `page`、`pageSize`、`sortBy`、`sortOrder`
- 过滤参数：优先显式 query 参数，不先做复杂 DSL

建议返回骨架：

```json
{
  "data": {},
  "meta": {
    "requestId": "req_xxx"
  },
  "error": null
}
```

## 4.2 状态枚举建议

### Session 状态

- `draft`
- `active`
- `completed`
- `archived`

### 阶段枚举

- `problem_definition`
- `research_analysis`
- `option_comparison`
- `decision_recommendation`

### StageRun 状态

- `pending`
- `running`
- `completed`
- `failed`
- `cancelled`
- `rolled_back`

### Recommendation 状态

- `generated`
- `accepted`
- `rejected`
- `needs_rework`

## 5. 第一版后端接口清单

下面按“页面 + 模块 + 读写动作”整理。

## 5.1 首页 / 会话入口接口

### `GET /api/v1/home/overview`

**用途**：首页聚合概览  
**服务页面**：首页  
**返回重点**：

- 最近会话
- 推荐继续处理的会话
- 最近调研主题
- 最近生成的决策建议

### `GET /api/v1/sessions`

**用途**：获取会话列表  
**服务页面**：首页、会话入口  
**建议参数**：

- `status`
- `currentStage`
- `keyword`
- `page`
- `pageSize`

### `POST /api/v1/sessions`

**用途**：创建新会话  
**服务页面**：首页  
**请求体建议**：

```json
{
  "title": "内部需求梳理工作台",
  "initialQuestion": "我们要做一个分阶段 AI 决策支持系统，第一版该怎么收敛？",
  "tags": ["决策支持", "MVP"]
}
```

**返回重点**：

- `sessionId`
- `currentStage`
- `status`

### `GET /api/v1/sessions/{sessionId}`

**用途**：获取单个会话基础信息  
**服务页面**：会话页、结果页  
**返回重点**：

- 标题
- 初始问题
- 当前阶段
- 会话摘要
- 最后更新时间

### `PATCH /api/v1/sessions/{sessionId}`

**用途**：更新会话基础信息  
**服务页面**：会话页  
**允许更新**：

- `title`
- `summary`
- `tags`
- `status`

### `POST /api/v1/sessions/{sessionId}/resume`

**用途**：恢复会话上下文并进入当前工作台  
**服务页面**：首页跳转、继续处理入口

## 5.2 决策工作台 / 阶段编排接口

### `GET /api/v1/sessions/{sessionId}/workspace`

**用途**：获取工作台聚合数据  
**服务页面**：决策会话页  
**返回重点**：

- 会话基础信息
- 阶段列表及状态
- 当前阶段详情
- 当前阶段候选方案
- 当前证据摘要
- 当前建议、风险、待确认项
- 最近模型执行摘要

这类接口的价值是前端首屏直出，不用页面自己拼 6 到 8 个接口。

### `GET /api/v1/sessions/{sessionId}/stages`

**用途**：获取阶段状态列表  
**服务页面**：左侧阶段导航

### `GET /api/v1/sessions/{sessionId}/stages/{stage}`

**用途**：获取指定阶段详情  
**服务页面**：会话页中间主区、右侧摘要区  
**返回重点**：

- 当前阶段说明
- 阶段状态
- 最近一次 `StageRun`
- 阶段结构化产物
- 关联候选方案和证据

### `POST /api/v1/sessions/{sessionId}/stages/{stage}/start`

**用途**：启动某阶段执行  
**服务页面**：会话页  
**请求体建议**：

```json
{
  "triggeredBy": "user",
  "contextPatch": {
    "goal": "先形成第一版需求简报"
  }
}
```

**返回重点**：

- `stageRunId`
- `status`
- `startedAt`

### `POST /api/v1/sessions/{sessionId}/stages/{stage}/rerun`

**用途**：重跑当前阶段  
**服务页面**：会话页  
**请求体建议**：

```json
{
  "reason": "补充调研支点后重跑",
  "keepExistingArtifacts": true
}
```

### `POST /api/v1/sessions/{sessionId}/stages/{stage}/rollback`

**用途**：回退到某阶段  
**服务页面**：会话页、结果页  
**请求体建议**：

```json
{
  "reason": "当前建议依据不足，回退到方案比较阶段"
}
```

### `PATCH /api/v1/sessions/{sessionId}/stages/{stage}/artifact`

**用途**：人工编辑当前阶段结构化产物  
**服务页面**：会话页  
**典型用途**：

- 编辑需求简报
- 修正阶段摘要
- 修改非目标/约束

### `GET /api/v1/stage-runs/{stageRunId}`

**用途**：获取某次阶段执行详情  
**服务页面**：运行详情弹层、调试面板  
**返回重点**：

- 阶段输入摘要
- 阶段输出快照
- 执行状态
- 耗时
- 模型调用列表

### `GET /api/v1/stage-runs/{stageRunId}/events`

**用途**：获取阶段执行事件流或事件列表  
**服务页面**：运行状态面板  
**说明**：

- 如果后续做实时更新，可对接 WebSocket/SSE
- 如果先不做实时，可先返回事件列表供轮询

## 5.3 调研页 / 证据模块接口

### `GET /api/v1/research-items`

**用途**：获取调研对象列表  
**服务页面**：调研页  
**建议参数**：

- `sessionId`
- `sourceType`
- `verdictTag`
- `keyword`

### `POST /api/v1/research-items`

**用途**：新增调研对象  
**服务页面**：调研页  
**请求体建议**：

```json
{
  "sessionId": "ses_001",
  "sourceType": "github",
  "title": "paperclip",
  "sourceUrl": "https://github.com/paperclipai/paperclip",
  "summary": "可借鉴其控制台、运行治理和实时事件设计"
}
```

### `GET /api/v1/research-items/{researchItemId}`

**用途**：获取调研对象详情  
**服务页面**：调研详情侧栏

### `PATCH /api/v1/research-items/{researchItemId}`

**用途**：更新调研对象  
**可更新字段建议**：

- `summary`
- `verdictTag`
- `borrowablePoints`
- `avoidPoints`
- `fitStages`

### `POST /api/v1/research-items/{researchItemId}/evidences`

**用途**：给调研对象新增证据  
**服务页面**：调研页详情区  
**请求体建议**：

```json
{
  "summary": "Paperclip 的控制面和运行面分离，适合借鉴为我们的工作台骨架",
  "tag": "architecture",
  "sourceRef": "research/Paperclip项目分析报告-深度版.md"
}
```

### `PATCH /api/v1/evidences/{evidenceId}`

**用途**：更新证据内容、标签和关联

### `DELETE /api/v1/evidences/{evidenceId}`

**用途**：删除错误证据  
**说明**：如果后续需要审计，可改软删除

### `POST /api/v1/evidences/{evidenceId}/link-candidates`

**用途**：把证据关联到候选方案  
**请求体建议**：

```json
{
  "candidateIds": ["cand_001", "cand_002"]
}
```

## 5.4 候选方案与比较接口

### `GET /api/v1/sessions/{sessionId}/candidates`

**用途**：获取当前会话候选方案列表  
**服务页面**：会话页、结果页

### `POST /api/v1/sessions/{sessionId}/candidates`

**用途**：新增候选方案  
**请求体建议**：

```json
{
  "title": "阶段式编排 + 角色化多模型 + 汇总裁决",
  "summary": "以阶段控制流程，以角色控制多模型分工",
  "sourceStage": "research_analysis"
}
```

### `GET /api/v1/candidates/{candidateId}`

**用途**：获取候选方案详情

### `PATCH /api/v1/candidates/{candidateId}`

**用途**：更新候选方案  
**允许更新字段建议**：

- `title`
- `summary`
- `pros`
- `risks`
- `statusLabel`
- `scoreSummary`

### `DELETE /api/v1/candidates/{candidateId}`

**用途**：删除候选方案  
**说明**：如果需要保留轨迹，建议改软删除

### `GET /api/v1/sessions/{sessionId}/comparison`

**用途**：获取比较视图聚合结果  
**服务页面**：会话页中间对比矩阵、结果页备选方案说明  
**返回重点**：

- 候选方案列表
- 主要比较维度
- 每个方案的优势/风险/证据覆盖
- 当前推荐倾向

### `POST /api/v1/sessions/{sessionId}/comparison/rebuild`

**用途**：基于当前候选方案和证据，重建比较结果  
**服务页面**：会话页  
**说明**：

- 第一版不一定要单独落比较表
- 但要有重建比较视图的能力

## 5.5 结果页 / 决策建议接口

### `GET /api/v1/sessions/{sessionId}/recommendation`

**用途**：获取当前会话的最新决策建议  
**服务页面**：结果页、会话页右侧当前建议区

### `POST /api/v1/sessions/{sessionId}/recommendation/generate`

**用途**：生成或重生成决策建议  
**请求体建议**：

```json
{
  "basedOnStageRunId": "sr_001",
  "includeAlternatives": true,
  "includeOpenQuestions": true
}
```

### `PATCH /api/v1/recommendations/{recommendationId}`

**用途**：人工编辑建议摘要、状态和下一步

### `POST /api/v1/recommendations/{recommendationId}/accept`

**用途**：采纳当前建议  
**服务页面**：结果页  
**请求体建议**：

```json
{
  "comment": "作为第一版架构方向采纳"
}
```

### `POST /api/v1/recommendations/{recommendationId}/reject`

**用途**：拒绝当前建议  
**服务页面**：结果页  
**请求体建议**：

```json
{
  "reason": "建议过于理想化，缺少实现约束"
}
```

### `POST /api/v1/recommendations/{recommendationId}/send-back`

**用途**：将建议退回到比较阶段重新评估  
**服务页面**：结果页  
**请求体建议**：

```json
{
  "targetStage": "option_comparison",
  "reason": "需要补充成本和实现复杂度的比较"
}
```

### `POST /api/v1/recommendations/{recommendationId}/export`

**用途**：导出结构化结果  
**说明**：

- 第一版可以先导出 Markdown 或 PDF 占位
- 真正导出逻辑后置

## 6. 核心数据表草案

以下是第一版建议的核心表结构。这里先给“字段层面可落地”的草案，不强绑数据库方言。

## 6.1 `sessions`

**用途**：保存一条决策会话的主信息

| 字段 | 类型建议 | 说明 |
|------|----------|------|
| id | uuid / varchar | 主键 |
| title | varchar(255) | 会话标题 |
| initial_question | text | 用户原始问题 |
| summary | text | 当前会话摘要 |
| current_stage | varchar(64) | 当前所处阶段 |
| status | varchar(32) | `draft/active/completed/archived` |
| owner_id | varchar(64) | 预留用户或操作者 |
| tags | json / jsonb | 标签数组 |
| latest_recommendation_id | varchar(64) | 当前最新建议 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |
| archived_at | datetime nullable | 归档时间 |

**建议索引**：

- `(status, updated_at desc)`
- `(current_stage, updated_at desc)`

## 6.2 `stage_runs`

**用途**：记录某会话某阶段的一次执行

| 字段 | 类型建议 | 说明 |
|------|----------|------|
| id | uuid / varchar | `stageRunId` |
| session_id | varchar(64) | 所属会话 |
| stage | varchar(64) | 阶段枚举 |
| run_id | varchar(64) | 运行链路标识 |
| status | varchar(32) | `pending/running/completed/failed/...` |
| triggered_by | varchar(32) | `user/system` |
| input_snapshot | json / jsonb | 阶段输入快照 |
| result_snapshot | json / jsonb | 阶段输出快照 |
| error_message | text nullable | 错误摘要 |
| started_at | datetime | 开始时间 |
| completed_at | datetime nullable | 完成时间 |
| duration_ms | bigint nullable | 执行耗时 |
| created_at | datetime | 创建时间 |

**建议索引**：

- `(session_id, stage, created_at desc)`
- `(run_id)`

## 6.3 `research_items`

**用途**：保存调研对象，如开源项目、论文、文章、案例

| 字段 | 类型建议 | 说明 |
|------|----------|------|
| id | uuid / varchar | 主键 |
| session_id | varchar(64) | 所属会话 |
| source_type | varchar(32) | `github/arxiv/web/manual` |
| title | varchar(255) | 调研对象标题 |
| source_url | text | 来源链接 |
| summary | text | 核心结论 |
| verdict_tag | varchar(32) | `borrow/caution/avoid` |
| borrowable_points | json / jsonb | 可借鉴点列表 |
| avoid_points | json / jsonb | 不建议借鉴点列表 |
| fit_stages | json / jsonb | 适合落位阶段 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |

**建议索引**：

- `(session_id, source_type)`
- `(session_id, verdict_tag)`

## 6.4 `evidences`

**用途**：保存某个调研对象下的证据片段或证据摘要

| 字段 | 类型建议 | 说明 |
|------|----------|------|
| id | uuid / varchar | 主键 |
| research_item_id | varchar(64) | 所属调研对象 |
| session_id | varchar(64) | 冗余保留，便于查询 |

## 7. 第一版建议补充字段修正

上面表结构里，以下字段建议强制统一：

- 所有主表都补 `created_at`
- 需要编辑的主表补 `updated_at`
- 所有可追踪执行链路的表补 `session_id`
- 所有和阶段执行有关的记录尽量挂 `stage_run_id` 或 `run_id`

这不是形式主义，而是为了避免后面分析和审计时拼不回链路。

## 9. 第一版埋点口子要求

虽然完整采集方案后置，但这一版接口和表结构已经要预留这些能力。

## 9.1 必记事件

- `session_created`
- `session_opened`
- `session_resumed`
- `stage_started`
- `stage_completed`
- `stage_rerun_requested`
- `stage_rollback_requested`
- `candidate_created`
- `candidate_updated`
- `candidate_deleted`
- `recommendation_generated`
- `recommendation_accepted`
- `recommendation_rejected`
- `model_invocation_started`
- `model_invocation_completed`
- `model_invocation_failed`

## 9.2 事件最小字段

```json
{
  "sessionId": "ses_001",
  "stage": "option_comparison",
  "eventName": "recommendation_generated",
  "actorType": "system",
  "actorId": "workflow-engine",
  "runId": "run_001",
  "stageRunId": "sr_001",
  "timestamp": "2026-04-08T15:00:00+08:00"
}
```

## 9.3 埋点与业务库边界

建议第一版先这样处理：

- 关键业务动作直接落 `user_actions`
- 分析页聚合结果定时写入 `usage_metrics`
- 更重的原始 trace 暂时只保留 `trace_ref`

这样做的好处是：

- 不会一开始就把采集系统做重
- 但也不会丢掉后续升级为正式遥测系统的入口

---

## 10. 推荐的实现顺序

如果接下来开始进入真正开发，建议按这个顺序落：

1. 先做 `Session + Workspace 聚合接口`
2. 再做 `StageRun + 阶段推进接口`
3. 再做 `ResearchItem / Evidence / CandidateOption`
4. 再做 `Recommendation`
5. 最后补 `Analytics` 和 `UserAction / UsageMetric`

原因：

- GUI 工作台最先依赖的是会话和工作台聚合数据
- 阶段推进是系统主链路
- 调研、候选方案和建议是逐步展开的结构化资产
- 分析页可以后跟，不应该抢主线

---

## 11. 当前结论

第一版后端不该做成“万能 AI 平台后端”，而应该做成：

> **一个面向 GUI 决策工作台的、以会话和阶段推进为中心的结构化控制后端。**

如果压缩成一句话：

> 先把 `会话 -> 阶段 -> 证据 -> 候选方案 -> 建议 -> 埋点` 这条数据链打通，第一版后端就站住了。
